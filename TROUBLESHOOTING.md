## Проблема 1: Connection refused при подключении из контейнера к Postgres

**Симптом:** `psycopg2.OperationalError: connection to sserver at "172.17.0.1", port 5432 faild: Connection refused`

**Как искал:** ошибка "refused" (а не timeout) означала, что пакет дошел до хоста, 
но порт там закрыт для этого адреса. Проверил `listen_addresses = postgresql.conf` и `ss -tulnp | grep 5432` -
 Postgres слушал только `127.0.0.1`.

**Причина:** `listen_addresses = 'localhost'` (дефолт) - сокет открыт только на loopback, а контейнер стучится через
 IP шлюза docker-моста (172.17.0.1), это не тоже самое, что localhost хоста.

**Фикс:** `listen_addresses = 'localhost,172.17.0.1'` в postgresql.conf, затем `systemctl restart postgresql`
(не reload - это настройка меняет сам список открываемых сокетов).


## Проблема 2: Postgres откланяет подключение - нет записи в pg_hga.conf

**Симптомы:** `FATAL: no pg_hba.conf entry for host "172.17.0.3", user "appuser", database "appdb", SSL encryption`

**Как искал:** заметил что ошибка изменилась по сравнению с прошлой - это уже не "Connection refused", а FATAL с явным 
тестом про pg_hba.conf. Значит, TCP-уровень пройден, проблема сместилась с "слушает ли Postgres" на "пускает ли Postgres".
 Проверил pg_hba.conf — в нём были только записи под 127.0.0.1/32 и ::1/128, записи под docker-подсеть не было вообще.
 Две строчки в самой ошибке (SSL / no encryption) — не два отдельных диагноза, а одна причина: psycopg2 сам пробует
 сначала зашифрованное соединение, потом откатывается на незашифрованное, и оба раза получает один и тот же отказ.

**Причина:** в ошибке 172.17.0.3, а не 172.17.0.1 это не опечатка и не баг — важный концептуальный момент. 172.17.0.1 в моем 
DATABASE_URL — это адрес назначения (куда стучимся). А pg_hba.conf матчит совсем другое поле — адрес источника, 
то есть с какого IP пришёл клиент. Docker при старте контейнера в дефолтной bridge-сети сам назначил ему динамический адрес
`(.2 уже занят другим контейнером — помнишь devops-app в выводе docker ps? — поэтому новому достался .3)`.
То есть Postgres корректно увидел, кто на самом деле стучится, и именно этого адреса нет в списке разрешённых.

**Фикс:** добавил в конец `pg_hba.conf`:
`sudo nano /etc/postgresql/18/main/pg_hba.conf`
Добавляешь в конец файла:
`host    appdb           appuser         172.17.0.0/16           scram-sha-256`
Применил через `sudo systemctl reload postgresql`.

# TROUBLESHOOTING — разобранные инциденты и ловушки

Этот файл — про то, что сломалось **само** (или из-за ручной ошибки): симптом,
доказательство по логам, причина, фикс. Плановые действия — в `RUNBOOK.md`.

---

## Инцидент: всплеск 502 строго в секунду reload при blue/green деплое

**Симптом:** во время нагрузочного теста с деплоем на 15-й секунде — 117×502
строго в момент выполнения `nginx -s reload`.

**Диагностика:** error-лог nginx показал на IP старого контейнера:

```
recv() failed (104: Connection reset by peer)
connect() failed (111: Connection refused)
```

**Причина:** сразу после `nginx -s reload` скрипт выполнял `docker stop`
старого контейнера. `reload` меняет upstream только для *новых* запросов —
старые nginx worker'ы продолжали доедать уже открытые in-flight запросы к
старому backend'у, а он к этому моменту уже был убит.

**Фикс:** между `reload` и `docker stop` — цикл ожидания drain:

```bash
for i in $(seq 1 20); do
  docker top nginx | grep -q "is shutting down" || break
  sleep 0.5
done
```

Только после этого — `docker stop` / `docker rm` старого контейнера.

**Результат:** повторный прогон с тем же профилем нагрузки — 0×502,
воспроизведено дважды подряд.

**Профилактика:** любой скрипт, который переключает upstream и затем убивает
старый бэкенд, обязан дождаться drain явной проверкой — `reload` не
гарантирует синхронного завершения уже открытых соединений.

## Пойманные ловушки

### `sed -i` на single-file bind-mount не долетает до контейнера

`sed -i` создаёт временный файл и переименовывает его на место оригинала —
на файловой системе это **новый inode**. Docker bind-mount примонтирован по
пути на момент старта контейнера и продолжает указывать на старый inode —
контейнер физически не видит правку.

Фикс — правка на месте, без смены inode:

```bash
sed '...' nginx.conf > /tmp/x && cat /tmp/x > nginx.conf
```

### `docker logs -f` без `--tail 0` тащит всю историю

Без `--tail 0` в файл сборщика логов сразу попадает вся история контейнера,
а не только новые записи с этого момента — засоряет данные анализа теста.

### Осиротевшие фоновые `docker logs -f`

Если скрипт падал раньше `cleanup` (из-за `set -e`), фоновый `docker logs -f`
от предыдущего прогона оставался жив и продолжал писать в тот же файл
параллельно со следующим прогоном → задвоение/порча данных.

Фикс: `trap cleanup EXIT` + `pkill` осиротевших процессов в начале скрипта,
до старта нового прогона.

### Ручные правки `nginx.conf` мимо `deploy.sh`

Минимум дважды пойман битый конфиг с буквальным `$COLOR`/`@COLOR` в файле
вместо подставленного значения — результат правки руками вместо прогона
через скрипт. `nginx.conf` не редактируется в `nano` напрямую — единственный
легитимный путь изменения — `deploy.sh`.

### `sed` без совпадения — тихая копия без изменений

Если паттерн не найден, `sed` не выдаёт ошибку, а просто копирует вход в
выход без изменений. Ловится только явной проверкой результата после
(сравнением цвета до/после или `diff`).

### `docker exec` на `Exited`-контейнере

`nginx -t` / `nginx -s reload` через `docker exec` требуют живого процесса
внутри контейнера. На остановленном контейнере — ошибка; сначала
`docker start`.

### Пропущенный `$` при ручном вводе переменной в скрипте

При переносе `pg-backup.sh` через `nano` на одной из четырёх одинаковых по
структуре строк (`pg_dump`/`dropdb`/`createdb`/`pg_restore`, все используют
`"$SOCKET_DIR"`) потерялся символ `$` — конкретно в строке `createdb`.
Результат: `createdb: error: could not translate host name "SOCKET_DIR" to
address` — команда попыталась резолвить буквальный текст `SOCKET_DIR` как
DNS-имя.

**Диагностика, которая довела до причины быстро:** если бы проблема была
в переменной/окружении, сломались бы все четыре строки одинаково — они все
используют `"$SOCKET_DIR"` одним и тем же образом. Сломалась только одна —
значит, дело не в системе, а в конкретной строке. `grep -n "SOCKET_DIR"
файл` подтвердил визуально: три строки с `$`, одна без.

**Профилактика:** после ручного переноса скрипта с несколькими одинаковыми
по структуре строками — сверить их все одной командой (`grep -n`), а не
доверять визуальной проверке в `nano`.

## Не баг, а особенность (не путать с реальной проблемой)

### `postgresql.service` в состоянии `active (exited)`

Debian/Ubuntu-пакет Postgres регистрирует верхнеуровневый мета-юнит
(`ExecStart=/bin/true`), который лишь убеждается, что реальный инстанс
(`postgresql@18-main.service`) запущен, и сам сразу завершается —
`active (exited)` для него ожидаемо, это не сбой. Реальное состояние
проверяется отдельно: `ss -tulpn | grep 5432` (живой процесс, слушающий
порт) или `systemctl status postgresql@18-main`.

### `Permission denied` на `ls` в директории бэкапов

`/var/backups/postgresql-appdb` — режим `700`, владелец `postgres`.
Обычный пользователь (`jaha_task_3`) физически не может заглянуть внутрь
без `sudo` — это подтверждение, что права настроены правильно, а не
поломка. `sudo ls` показывает содержимое как обычно.

## Инцидент: nginx упал (137) после `docker restart` в обход systemd

**Симптом:** после `docker restart nginx` контейнер поднимался на пару
минут и падал с кодом `137`, повторно, несколько раз подряд.

**Как искал:** `docker inspect --format 'OOMKilled=... Error=...'` показал
`OOMKilled=false` — гипотеза про нехватку памяти отпала. `systemctl status
nginx.service` вскрыл настоящую причину: `ExecStop=/usr/bin/docker stop
nginx (code=exited, status=0/SUCCESS)` — остановка была не сбоем, а
**самим systemd**.

**Причина:** у nginx, как и у backend, был свой systemd-юнит
(`nginx.service`, `Type=simple` + `docker start -a nginx` как foreground-
процесс). `docker restart` в обход юнита разорвал это присоединение;
systemd увидел, что его главный процесс завершился не по его команде,
инициировал `ExecStop`, тот не уложился в грейс-период на уже
дестабилизированном контейнере — Docker эскалировал до SIGKILL.

**Фикс на момент инцидента:** для любого контейнера под systemd-
супервизией — управление жизненным циклом только через `systemctl
stop/start/restart <unit>`, никогда напрямую `docker restart/stop/kill`.

**Исторический статус:** сам первоисточник проблемы (systemd-супервизия

**Профилактика на будущее:** перед любой ручной командой над контейнером,

## Ловушка: `docker compose stop/rm` тихо ничего не делает без лейблов

**Проверка перед тем, как довериться compose-командам:**

## Ловушка: `git restore` (как и `sed -i`) на bind-mount создаёт новый inode

Не только `sed -i` — любой инструмент, пишущий «безопасно» (temp-file +
rename, вместо правки на месте), меняет inode файла. Docker bind-mount
привязан к конкретному inode на момент старта контейнера. `git restore`
на файле, который смотрит в контейнер через single-file bind-mount,
восстанавливает содержимое на диске корректно — но контейнер продолжает
видеть старую (возможно, повреждённую) версию, пока его не пересоздать
(`docker restart`/`systemctl restart <unit>`).

**Диагностика:** расхождение между `wc -c file` на хосте и
`docker exec <container> wc -l /путь/в/контейнере` — если числа не
совпадают при, казалось бы, восстановленном файле, дело в inode, не в
содержимом.

## Ловушка: два `>` в одной команде — bash обнуляет обе цели ДО выполнения

```bash
sed 's/.../.../' file > /tmp/x > file    # ОШИБКА
```
Bash открывает (и truncate'ит) каждую `>`-цель по очереди при разборе
команды, ещё до её запуска — `file` обнуляется вторым, раньше, чем `sed`
успевает его прочитать. Результат — пустой `file`, без единого сообщения
об ошибке.

**Фикс:** строго два отдельных шага, никогда не смешивать несколько `>`
в одной строке:
```bash
sed 's/.../.../ file > /tmp/x
cat /tmp/x > file
```

## Ловушка: `sshd_config.d/*.conf` побеждает основной `sshd_config`

## Не баг, а особенность: `docker image prune -a` освобождает меньше, чем обещал `docker system df`

каждый тег. Реальное удаление освобождает уникальные, больше никем не
используемые байты — на практике оказалось на порядок меньше заявленного

## Вариант A: dockerd стал единственным владельцем жизненного цикла

**Исходная проблема:** у `backend-blue`/`backend-green`/`nginx` было до
трёх независимых механизмов, трогающих один контейнер на разных этапах
его жизни — compose создавал, systemd перезапускал при падении,
`deploy.sh` удалял старый цвет напрямую мимо обоих. Работало три недели
без инцидентов, но каждый из двух инцидентов выше (nginx 137, несинхронный
`backend.service`) — прямое следствие именно этой схемы.

**Решение:** `restart: unless-stopped` на всех трёх сервисах в
`docker-compose.yml`, `backend.service`/`nginx.service`/
`current-color.sh` удалены целиком. Единственный владелец — dockerd.

**Почему `unless-stopped` безопасен для blue/green без специальной
логики.** Политика не читает код выхода и не знает о существовании других
контейнеров — она смотрит на отдельный флаг «был ли контейнер явно
остановлен командой `docker stop`». `deploy.sh` на шаге уборки старого
цвета и так уже делает `docker stop` + `docker rm` — то есть явно
останавливает контейнер **перед тем**, как он вообще исчезает физически.
Специальная blue/green-логика не понадобилась.

**Подтверждено экспериментом на одноразовых контейнерах** (до применения
на проде):
```bash
docker run -d --name test-active --restart unless-stopped alpine sleep 3600
docker run -d --name test-standby --restart unless-stopped alpine sleep 3600
docker stop test-standby
sudo systemctl restart docker
docker ps -a --filter name=test-
# test-active снова Up сам; test-standby остался Exited
```

**Подтверждено на проде:** реальный `systemctl restart docker` — backend
и nginx поднялись сами, без единой ручной команды; затем полный цикл
`deploy.sh` (blue→green) прошёл до конца без финального шага синхронизации
с systemd, который раньше был обязателен.

## Инцидент: `docker.service` не поднимался после рестарта — опечатка в hook-скрипте

**Симптом:**
```
Job for docker.service failed because the control process exited with error code.
```
`systemctl status docker.service` показал `ExecStartPost` с
`status=1/FAILURE`, при этом сам `ExecStart` (dockerd) — `0/SUCCESS`.

**Диагностика:** `journalctl -u docker.service` выявил точную строку:
```
docker-user-fw.sh[...]: iptables: No chain/target/match by that name.
```
`sudo bash -x /usr/local/sbin/docker-user-fw.sh` показал, на какой именно
команде обрыв: последняя строка скрипта содержала `DCOKER-USER` вместо
`DOCKER-USER` — переставлены буквы.

**Причина (две накладывающиеся):**
1. Опечатка в имени цепочки `iptables` — сама по себе безобидная ошибка.
2. Systemd считает весь старт юнита неудачным, если `ExecStartPost`
   завершился с ошибкой, и шлёт `SIGTERM` уже поднявшемуся `dockerd` —
   даже если сам демон стартовал нормально.
3. Docker **без `live-restore`** при штатном (не аварийном) завершении
   демона останавливает все работающие контейнеры. Это не то же самое,
   что аварийное падение (`kill -9`), при котором `containerd-shim`
   (перепородительствованный на PID 1) продолжает держать контейнеры
   живыми независимо от `dockerd`.

**Фикс:** опечатка исправлена, `systemctl reset-failed docker.service`
(демон упёрся в лимит частых рестартов — `Start request repeated too
quickly`), `systemctl start docker.service`. Контейнеры к этому моменту
были остановлены штатным завершением демона и не поднялись сами — их
восстановили вручную тогдашними средствами (`backend.service`/
`nginx.service restart`, `docker compose up -d` для мониторинга), ещё до
перехода на Вариант A.

**Профилактика:** любой `ExecStartPost`/`ExecStartPre` hook у критичного
юнита — проверять вручную (`bash -x`) перед тем, как доверять его
systemd; провал хука может уронить уже успешно стартовавший процесс.

## Ловушка: цепочка `DOCKER-USER` пересоздаётся пустой при каждом старте демона

**Контекст:** требовалось ограничить доступ к Prometheus (`:9090`, VM-1)
только с VM-2. `ufw` не видит трафик к портам, опубликованным Docker —
правила Docker живут в цепочке `FORWARD`, `ufw` фильтрует `INPUT`.

**Фикс:** правила `ACCEPT`/`DROP` добавляются в `DOCKER-USER` — цепочку,
которую Docker гарантированно проверяет до своих собственных правил в
`FORWARD`. Но она создаётся заново, пустой, при каждом старте `dockerd` —
правила нужно переустанавливать на каждый старт, не один раз руками.

**Реализация:** идемпотентный скрипт (`-D ... || true`, затем `-I ...`
заново) через `systemd` drop-in `docker.service.d/dockeruser-fw.conf` →
`ExecStartPost=/usr/local/sbin/docker-user-fw.sh`.

## Ловушка: `-I CHAIN N` вставляет на позицию N в ТЕКУЩЕМ состоянии цепочки

**Симптом:** после первой попытки настройки правил `DOCKER-USER` — VM-2
получала `Connection timed out` к порту `9090`, хотя правило `ACCEPT` для
её адреса было добавлено.

**Диагностика:**
```
num   pkts bytes target     prot opt source               destination
1       33  2008 DROP       tcp  --  0.0.0.0/0            ...  dpt:9090
2        0     0 ACCEPT     tcp  --  192.168.64.5         ...  dpt:9090
```
`DROP` оказался первой строкой, `ACCEPT` — второй: пакеты от VM-2 матчили
`DROP` раньше, чем успевали дойти до `ACCEPT`.

**Причина:** `iptables -I CHAIN N` вставляет правило на позицию N
**относительно текущего состояния цепочки в момент выполнения команды**,
а не относительно порядка, в котором команды задуманы. Если команда с
`DROP` фактически выполнилась раньше (из-за особенности многострочного
ввода, см. ниже) — она и заняла первую позицию.

**Фикс:** оба правила удалены (`-D`) и вставлены заново одной строкой
через `&&`, гарантируя порядок выполнения:
```bash
sudo iptables -I DOCKER-USER 1 -p tcp --dport 9090 -s 192.168.64.5 -j ACCEPT && \
sudo iptables -I DOCKER-USER 2 -p tcp --dport 9090 -j DROP
```

## Находка: пакетный `nginx` на хосте VM-1 обнаружился только после удаления своего юнита

**Симптом:** после удаления кастомного `/etc/systemd/system/nginx.service`
(в рамках перехода на Вариант A) команда `systemctl list-unit-files | grep
nginx` неожиданно продолжила показывать `nginx.service` — `disabled`.

**Причина:** юниты в `/etc/systemd/system/` маскируют одноимённые юниты
из `/usr/lib/systemd/system/`. На VM-1 когда-то был установлен пакет
`nginx`/`nginx-common` (`apt`) со своим штатным юнитом — наш кастомный
файл всё это время просто перекрывал его собой, не давая увидеть.

**Риск:** случайный `systemctl enable --now nginx` занял бы порты
`80`/`443` на хосте напрямую, в обход Docker — конфликт с работающим
nginx-контейнером.

**Фикс:**
```bash
sudo apt remove --purge nginx nginx-common
sudo systemctl mask nginx.service
```
`mask` — поверх `purge`, на случай если пакет не подчистил бы юнит-файл
сам; теперь юнит — символьная ссылка на `/dev/null`, не включается даже
случайным `systemctl enable`.

### Рассинхрон часов VM после паузы UTM

**Симптом.** Self-hosted раннер на VM-1 перестал принимать задания: job висел в очереди, раннер офлайн.
Регистрационный токен оказался «истёкшим» на 44 минуты раньше времени сервера GitHub.

**Причина.** Пока VM стоит на паузе в UTM, её часы не идут, а после возобновления гость этого не замечает.
Chrony по умолчанию узнаёт об отставании только на следующем опросе источников, а интервал опроса вырастает 
до ~17 минут (`maxpoll 10`). К тому же штатная настройка `makestep 1 3` разрешает перескочить на правильное 
время только в первые 3 обновления после старта демона. После пакета ранней паузы лимит давно исчерпан, 
и часы подстраивались бы плавно, то есть часами.

**Решение** (на обеих VM, правки в `/etc/`, вне репозитория):
- `/etc/chrony/chrony.conf`: `makestep 1 3` → `makestep 1 -1` (шаг разрешён всегда, без лимита);
- `/etc/chrony/sources.d/ubuntu-ntp-pools.sources`: в конец каждой строки `pool` добавлено `maxpoll 6` (опрос не реже раза в 64 с);
- `sudo systemctl restart chrony`.

**Проверка.**
- `chronyc sources`: колонка `Poll` держится на 6 (проверено через 15+ минут после перезапуска);
- на VM-2 часы сдвинуты командой `sudo date -s '+10 minutes'`: chrony сам вернул их назад примерно за 2–3 минуты, 
в журнале `System clock wrong by -599.99 seconds`.

**Мгновенное исправление.** `sudo chronyc makestep` ставит правильное время сразу, без ожидания опроса.

**Ограничения.**
- Правка лежит вне репозитория: при пересоздании VM её нужно повторить.
- Проверка со сдвигом выполнена только на VM-2 (на VM-1 раннер); настройки на VM-1 те же.
- Реальная пауза UTM: *не проверено* (обновить после проверки).
