# DevOps Backend Stack — README

## Что это

Учебный проект (стажировка DevOps, Задание 3 закрыто, Этап 0 Задания 4
закрыт): backend + nginx на одном хосте, PostgreSQL — на втором, полная
TLS-цепочка между всеми компонентами, zero-downtime деплой через
blue/green, контейнеры с минимальными привилегиями, бэкап БД, алертинг,
полный стек метрик (Prometheus + Grafana).

Единственный владелец жизненного цикла контейнеров на VM-1 — сам Docker
(`dockerd`), не systemd. Исключение — Grafana на VM-2: она живёт как
обычный apt-пакет под systemd, потому что там нет и не планируется Docker.

## Архитектура

```
Клиент ──HTTPS──► nginx :443 (VM-1, 192.168.64.3; :80 → 443)
                    │
                    ├─ /api/* ──► backend-blue | backend-green :8000 (активен один)
                    │               ├─► Postgres (VM-2:5432, TLS): метаданные, статусы
                    │               ├─► Redis (redis:6379, пароль): кеш и очередь задач (XADD)
                    │               └─► MinIO (minio:9000): PUT и DELETE объектов
                    └─ /s3/* ───► MinIO :9000 (rewrite убирает /s3; только GET по presigned-ссылке)

worker ──► Redis Streams (XREADGROUP, XACK)
       ──► MinIO (чтение) ──► SHA-256, размер, тип ──► Postgres (результат)

VM-1, systemd: сверка Postgres/MinIO, бэкапы Redis и MinIO, сторож бэкапов,
               health-alert, alert-notifier
VM-1, мониторинг: Prometheus :9090 (доступен только VM-2) ◄─ backend /metrics,
               cAdvisor, node-exporter (сеть monitoring-net)
VM-2 (192.168.64.5): PostgreSQL 18 (только hostssl, UFW: только VM-1),
               Grafana 13.2.1 (читает Prometheus на VM-1), pg-backup.timer, сторож бэкапа
```

Единственный владелец жизненного цикла контейнеров на VM-1 — dockerd
(`restart: unless-stopped`): backend, worker, nginx, Redis, MinIO, Prometheus,
cAdvisor, node-exporter. Проверено перезагрузкой VM-1 2026-10-08: все контейнеры
поднялись сами.

TLS построен на кастомном CA (`ca.crt`) с корректными SAN-полями
(`DNS:app.local`, `DNS:db`). CN сознательно не используется — современные
клиенты его игнорируют (RFC 6125), проверка идёт по SAN.

Все три сервиса (`backend-blue`, `backend-green`, `nginx`) описаны в одном
`docker-compose.yml` — общие для обоих цветов настройки (`read_only`,
`cap_drop`, `env_file`, монтирование сертификата) заданы один раз через
YAML-якорь `x-backend-common`, а не дублируются. Секрет (`DATABASE_URL`)
живёт в `.env.backend` (вне git), читается через `env_file`.

## Docker-хардненинг

| | До | После |
|---|---|---|
| Сборка образа | обычная | multi-stage build |
| Пользователь в контейнере | root | non-root `appuser` |
| Рантайм-флаги (backend) | — | `--read-only --cap-drop ALL` |
| Базовый образ | плавающий тег | `python:3.12-slim` закреплён по дайджесту |
| Зависимости (`requirements.txt`) | без версий | версии зафиксированы (`pip freeze`, проверено идентичным пересборкой) |

Хардненинг проверен не в теории, а прогоном реального стека с
`--read-only --cap-drop ALL`, отдельно подтверждено поведение при OOM.

**Известная асимметрия, всё ещё открыта:** у `nginx`-контейнера нет
`--read-only`/`--cap-drop ALL` — в отличие от backend. nginx слушает порт
443 (<1024) — для `--cap-drop ALL` потребуется явно вернуть
`--cap-add NET_BIND_SERVICE`, иначе не забиндится порт. Осознанно не
исправлено, задокументировано как техдолг — см. `TROUBLESHOOTING.md`.

## Zero-downtime деплой (blue/green)

Два контейнера backend (`backend-blue`, `backend-green`). Активный выбирается
одной строкой в `nginx.conf`:

```
set $backend_upstream backend-<color>:8000;
```

nginx резолвит DNS каждого апстрима динамически (`resolver 127.0.0.11 valid=10s`),
поэтому переключение — это правка конфига + `nginx -t` + `nginx -s reload`,
без пересоздания nginx-контейнера.

Единственный источник правды о текущем активном цвете — сам `nginx.conf`
(не отдельный state-файл): `deploy.sh` каждый раз вычисляет его через
`grep -oP '(?<=backend-)[a-z]+(?=:8000)'`.

`nginx.conf` и `monitoring-stack/targets/backend.json` отслеживаются в git
как шаблоны, но помечены `git update-index --skip-worktree` — `deploy.sh`
переписывает их на каждом свапе, и без этого флага репозиторий никогда не
был бы «чистым» после обычной работы. На свежем `git clone` оба файла всё
равно приходят с рабочим содержимым, а не пустые.

### deploy.sh и docker-compose

Новый цвет собирается и поднимается через compose:
```bash
docker compose build backend-$COLOR
docker compose up -d --no-deps backend-$COLOR
```
Старый цвет убирается напрямую через `docker stop`/`docker rm`, не через
`docker compose stop`/`rm` — сознательное решение: compose управляет только
контейнерами со своими лейблами (`com.docker.compose.*`), а гарантии, что
удаляемый контейнер был создан именно через compose, нет. Голый
`docker stop`/`rm` по имени работает одинаково независимо от происхождения
контейнера.

Деплой больше не заканчивается синхронизацией с systemd — этот шаг был
нужен только пока `backend.service` супервизировал контейнер отдельно от
Docker. После перехода на единого владельца (см. ниже) синхронизировать
стало нечего: dockerd сам знает, какой контейнер жив, по факту его
собственного состояния.

### Как запускается деплой (GitHub Actions runner)

Деплой на VM-1 запускает self-hosted runner GitHub Actions — служба
`actions.runner.molochik98-prog-task-2.jahongir.service`. Его каталог
`actions-runner-task2/` лежит внутри рабочей копии, но в `.gitignore`
(`git ls-files` и `git log` его не содержат; внутри лежат `.credentials` и
ключ регистрации). Workflow `.github/workflows/deploy.yml` срабатывает только
на `push` в `main` (триггера `pull_request` нет) и делает два шага:
`git pull origin main` в `/home/jahongir/devops-backend`, затем `./deploy.sh`.
Это не второй механизм деплоя, а запуск того же `./deploy.sh`.
Что из этого следует:

- Пуш в `main` — это выкатка на VM-1. Резервная копия работы идёт в другую
  ветку: `git push origin HEAD:task4-wip`, деплой при этом не запускается.
- Выкатывается рабочая копия на VM-1: `deploy.sh` собирает образ из неё.
- Миграции БД применяются на VM-2 вручную и до пуша в `main`: код,
  ожидающий новую колонку, не должен выкатиться раньше миграции.
- Проверено 2026-10-08: служба runner в состоянии `active` после
  перезагрузки VM-1. Сам запуск workflow в этот день не проверялся.


### nginx тоже под compose

Правка `nginx.conf` для переключения активного цвета идёт через безопасную
запись на месте: `sed ... > /tmp/x && cat /tmp/x > nginx.conf` (не `sed -i`,
не `docker restart` — оба меняют inode или рвут супервизию, см.
`TROUBLESHOOTING.md`), затем `nginx -t` + `nginx -s reload` внутри уже
работающего контейнера — сам контейнер не пересоздаётся при обычном
деплое.

## Владение жизненным циклом контейнеров

Единственный владелец — `dockerd`. Все сервисы (`backend-blue`,
`backend-green`, `worker`, `nginx`, `redis`, `minio`, `prometheus`, `cadvisor`,
`node-exporter`) стоят
на `restart: unless-stopped`, `stop_grace_period: 15s`. Никакого systemd
поверх контейнеров на VM-1 больше нет.

**Почему `unless-stopped`, а не `always` или ручной рестарт.** Docker
хранит отдельный, не связанный с кодом выхода флаг — был ли контейнер явно
остановлен вручную (`docker stop`, `docker kill`: см. ниже). `unless-stopped` при перезапуске демона
проверяет именно его: контейнер, который `deploy.sh` явно остановил при
свапе цвета, остаётся выключенным; контейнер, который был жив и погас
вместе с демоном, поднимается сам. Политика применяется к каждому
контейнеру независимо — ей не нужно знать, активен ли сейчас
`backend-blue` или `backend-green`.

**Подтверждено дважды, не только по документации:**
- на одноразовых тестовых контейнерах (`test-active`, явно остановленный
  `test-standby`) — после `systemctl restart docker` активный поднялся
  сам, остановленный остался выключен;
- на проде — через реальный `systemctl restart docker`: backend и nginx
  поднялись сами, без единой ручной команды.

**Что `unless-stopped` считает ручной остановкой (найдено 2026-10-09).** Флаг
ставит не только `docker stop`: его ставит и `docker kill`, и даже
`docker kill -s HUP`, после которого контейнер продолжает работать. После ребута
VM-1 2026-10-09 Prometheus не поднялся: в журнале `dockerd` за прошлую загрузку
у него `hasBeenManuallyStopped=true`, у остальных контейнеров `false`. По истории
команд (`docker kill -s HUP` для перечитывания правил) и записи о перезагрузке
конфигурации в логе Prometheus (12:26 UTC 2026-10-08) причина в этом. Механизм
воспроизведён на одноразовых контейнерах:

| Действие | Состояние | Перезапусков | `HasBeenManuallyStopped` |
|---|---|---|---|
| `docker kill -s HUP` | Up | не замерялось | true |
| `docker kill` | Exited (137) | 0 | true |
| `kill -9` по PID процесса (имитация падения) | Up, перезапущен | 1 | false |
| `docker start` после ручной остановки | Up | не замерялось | false |
| `docker exec ... kill -HUP 1` | Up | не замерялось | false |

Prometheus не работал с загрузки VM-1 (04:13 UTC) до ручного `docker start`
около 05:30 UTC. Сторож `alert-notifier` прислал «Prometheus недоступен 3 минуты
подряд» в 04:18 UTC и «снова доступен» в 05:31 UTC, по одному сообщению. Правила:
конфиг Prometheus перечитывать через `docker exec monitoring-stack-prometheus-1
kill -HUP 1`, а не через `docker kill`; после опытов со `stop` и `kill`
контейнер поднимать явным `docker start`. `scripts/stage4-proof.sh` убивает
worker через `docker kill` и запускает `docker start`: это доказательство потери
задачи, а не проверка автоперезапуска. Автоперезапуск после настоящего падения
процесса проверяется в `CHAOS.md`, эксперимент 4.

Эта схема заменила связку `backend.service`/`nginx.service` +
`current-color.sh` (оба файла удалены) — три независимых механизма
управляли одним контейнером на разных этапах его жизни, что дважды роняло
сервис на практике. Полная история инцидента, который доказал
необходимость перехода — в `TROUBLESHOOTING.md`.

**Диск под будущий рост.** Корневой том VM-1 расширен с 18.5 до 28 ГБ,
выделен отдельный 6-гигабайтный том `minio-data` под `/srv/minio` (fstab по
UUID, `nofail`, иммутабельная точка монтирования до монтирования) —
переживает `docker rm`, заполнение не заденет корень диска. Подготовлено
для Задания 4, сейчас занят MinIO (`/srv/minio/data`).

## Мониторинг

**Prometheus, cAdvisor, node-exporter — на VM-1**, рядом со своими целями,
под dockerd с `unless-stopped`. Все три образа закреплены тегом и
дайджестом. Prometheus скрейпит backend через `file_sd_configs`
(`monitoring-stack/targets/backend.json`, переписывается `deploy.sh` на
каждом свапе цвета), себя, cAdvisor, node-exporter.

Порт `9090` опубликован Docker-ом на `0.0.0.0`, но закрыт для всех, кроме
VM-2, правилом в цепочке `DOCKER-USER` — она пересоздаётся пустой при
каждом старте демона, поэтому правило переустанавливается автоматически
через `systemd` drop-in (`docker.service.d/dockeruser-fw.conf` →
`ExecStartPost`, идемпотентный скрипт). `ufw` тут бессилен: Docker пишет
правила в цепочку `FORWARD`, минуя `INPUT`, где живут правила `ufw`.
Скрипт и drop-in лежат в репозитории (`scripts/docker-user-fw.sh`,
`systemd/docker.service.d/dockeruser-fw.conf`) и копируются в
`/usr/local/sbin/` и `/etc/systemd/system/docker.service.d/`. Что правило
переживает перезагрузку, проверено 2026-10-08: после `reboot` VM-1 в
`iptables -S DOCKER-USER` оба правила на месте, с Mac на 9090 таймаут и по
IPv4, и по IPv6 (чем именно закрыт IPv6, не выясняли). Побочный эффект
`ExecStartPost`: если скрипт упадёт, `docker.service` не стартует (по
семантике systemd, не проверялось). Выбрано осознанно: лучше громкий отказ,
чем тихо открытый порт.

**Grafana — на VM-2**, установлена из `apt.grafana.com`, версия `13.2.1`
зафиксирована (`apt-mark hold`). Из полутора десятков plugin-datasource,
которые Grafana ставит по умолчанию, оставлен только Prometheus
(`disable_plugins` в `grafana.ini`) — экономия около 300 МиБ на VM с
1.6 ГБ RAM. Источник данных задан как код
(`/etc/grafana/provisioning/datasources/prometheus.yml`, `editable: false`,
указывает на `http://192.168.64.3:9090`). Порт `3000` закрыт `ufw` для
всех, кроме рабочей машины оператора.

Три дашборда (`Backend request rate`, `Docker monitoring`,
`Node Exporter Full`) экспортированы в формате **Classic JSON** (не V2
Resource — он не годится для повторного импорта через «Upload JSON file»)
и лежат в `monitoring-stack/dashboards/` — переносимы на любой новый
инстанс Grafana без ручной настройки панелей.

## Бэкапы

У каждого хранилища свой способ, но порядок один: снять копию → проверить, что из неё
можно восстановиться → только потом ротация и метка успеха `.last-success`. Сбой любого
шага даёт ненулевой код, и `OnFailure=backup-failure@%n.service` присылает хвост журнала
в Telegram. Права на каталоги и файлы выставляют сами скрипты.

| Система | Где | Что снимаем | Как проверяется восстановление | Сколько хранится |
|---|---|---|---|---|
| Postgres | VM-2, `pg-backup.sh` от пользователя `postgres` | `pg_dump -Fc` через Unix-сокет | `pg_restore --exit-on-error` в отдельную БД `appdb_restore_check`; число строк каждой таблицы в копии должно лежать между счётом до дампа и после | 7 последних дампов в `/var/backups/postgresql-appdb` (каталог 700, файлы 600) |
| Redis | VM-1, `redis-backup.sh` | `BGSAVE`, копия `dump.rdb` | `redis-check-rdb`, затем отдельный одноразовый инстанс на копии (`--network none`): ключей не 0, если в источнике не 0, и `XLEN queue:files:dead` совпадает с источником | 7 последних в `/var/backups/redis` |
| MinIO | VM-1, `minio-backup.sh` | `mc mirror` bucket `uploads` в `uploads-backup/<дата-время>`, затем выгрузка копии в обычные файлы | каждый ключ с размером из списка источника (снят до копирования) есть в копии; выгрузка на диск совпадает со списком копии | 3 копии в `uploads-backup`, одна выгрузка в `/var/backups/minio/latest` |

Root-ключи MinIO нужны только `minio-backup.sh` (читает их из `.env`); приложению они
не передаются. Проверенная копия Postgres, у которой не сошлись данные, переименовывается
в `*.dump.failed`; такие файлы шаблон ротации (`appdb-*.dump`) не трогает (по коду, не
проверялось).

### Когда бэкапы запускаются на самом деле

Таймеры: Postgres 03:00 на VM-2 (случайная задержка до 300 с), Redis 03:20 и MinIO 03:40
на VM-1 (до 120 с), у всех `Persistent=true`. Обе VM выключаются на ночь (`last -x` на
VM-1: выключена 7 окт 13:05, включена 8 окт 04:39; выключена 8 окт 12:43, включена
9 окт 04:13), поэтому в 03:00–03:40 запуска не происходит: пропущенный запуск
догоняется сразу после загрузки. Это видно по именам дампов Postgres за 5–9 окт (время
04:26, 04:36, 04:46, 04:40, 04:16) и по запуску Redis и MinIO 9 окт в 04:14:56, через
минуту после загрузки VM-1. Следствия: копия снимается раз за включение, а не в 03:00;
«7 последних» означает 7 копий, а не 7 суток (8 окт дампов было три: в 04:40, 12:00 и
12:19); граница возможной потери данных равна времени между включениями. Расписание в
юнитах не менялось.

### Копии вне VM-1: pull с VM-2

До 2026-10-09 копии Redis и MinIO лежали на той же VM-1, а bucket `uploads-backup` был в
той же MinIO на том же томе `/srv/minio`: удаление тома уничтожало и бэкап. Теперь:

- После проверки скрипты выкладывают каталог `latest/`: данные, `SHA256SUMS` и `COMPLETE`
  с меткой времени. Он собирается как `latest.new` и подменяется целиком. Группа
  `backup-read` читает только `latest/`; история и `.last-success` остаются за root.
  Выгрузка MinIO делается одноразовым контейнером из того же образа (по digest) с
  `--read-only`, `--cap-drop ALL`, вне тома `/srv/minio`.
- На VM-1 пользователь `backup-pull` с заблокированным паролем и ключом
  `restrict,from="192.168.64.5",command="/usr/bin/rrsync -ro /var/backups"`: только
  чтение, только с VM-2, оболочки нет.
- На VM-2 пользователь `vm1-pull` (оболочка `nologin`), ключ ed25519 без пароля (таймер
  работает без человека). `known_hosts` с ключом хоста VM-1, отпечаток
  `SHA256:ceA4rB8JJUiPPoaNiJCfMw0UzlXd9hninBt+4n1Zx4E` сверен с `ssh-keygen -lf` на VM-1;
  `StrictHostKeyChecking=yes`.
- `vm1-pull.timer`: через 5 минут после загрузки и затем раз в час (раньше сторожа,
  у которого 10 минут). `vm1-pull.sh` читает `COMPLETE`; если такая копия уже есть,
  ничего не качает. Иначе `rsync` (без `--delete`), `sha256sum -c`, число файлов равно
  числу строк `SHA256SUMS`, повторное чтение `COMPLETE` (`latest` не сменился), до трёх
  попыток. Копия ложится в `/var/backups/vm1/<система>/<время COMPLETE>`, затем ротация
  (7 копий), затем `.last-success` со временем создания копии на VM-1.
- VM-1 недоступна (код `rsync` 255): `WARN` и код 0, потому что ночью VM выключены.
  Свежесть проверяет сторож.

### Что бэкапить в Redis

Кеш не нужен: наполнится заново. Очередь меняет ответ слабо: если задачи потеряны,
`sweeper` в worker находит файлы по статусам в Postgres (`uploaded` старше 2 минут,
`processing` старше 10 минут, `db.list_stale`) и ставит их заново; на практике проверено
для `uploaded` (`sweeper re-enqueued`). Невосстановимо только то, чего нет в Postgres:
счётчики доставок и содержимое мёртвой очереди (файлы из неё в Postgres помечены
`failed`). Поэтому снимок Redis это страховка и материал для разбора мёртвой очереди, а
не единственный носитель задач.

### Что бэкапы не защищают

- Обе VM работают в UTM на одном Mac (подсеть 192.168.64.0/24): потеря Mac уничтожает всё.
- Дампы Postgres лежат только на VM-2, на той же VM, что и база; pull их не забирает.
- Postgres проверяется по числу строк, не по содержимому. MinIO: ключи и размеры между
  bucket и выгрузкой; контрольные суммы SHA-256 покрывают выгрузку на диске и путь
  VM-1 → VM-2, но не сравнение с содержимым bucket.
- Pull забирает только текущий `latest`: если между его запусками VM-1 сняла две копии,
  промежуточная на VM-2 не окажется.
- `from=` в ключе не проверялся: для этого нужен запрос с другого адреса. `rrsync -ro
  /var/backups` показывает весь каталог, но файлы с доступом на чтение там только
  системные (`dpkg.*`, `apt.*`), их и так читает любой локальный пользователь VM-1.
- Проверка на каждом запуске это не учение по восстановлению. Учение (снести три
  хранилища, поднять из бэкапов по `RUNBOOK.md`, засечь время) ещё не проведено.

### Память backend при загрузке больших файлов (ловушка 1.2)

Замер: `scripts/upload-mem-test.sh <МиБ>`. Лимит контейнера 256 МиБ, без swap.
Базовый anon простаивающего backend: 45-52 МиБ.

| Размер файла | Пик anon   | Пик file (кеш)   | OOMKilled       | Временных файлов      | SHA-256 |
|--------------|------------|------------------|-----------------|-----------------------|---------|
| 50 МиБ       | 60 и 95 МиБ (2 прогона, по 2 замера, ненадёжно) | 69 / 77 МиБ | нет | 0 | совпал  |
| 500 МиБ      | 95 МиБ     | 159 МиБ          | нет             | 0                     | совпал  |
| 2048 МиБ     | 95 МиБ     | 196 МиБ          | нет             | 0                     | совпал  |

Вывод: при росте файла в 4 раза (500 -> 2048) пик anon не изменился, то есть
память не растёт пропорционально размеру файла. Тело запроса идёт в MinIO
кусками по 10 МиБ.

Почему `/tmp` не годится для тестового файла: на VM-1 это tmpfs (814 МБ в
оперативной памяти), поэтому `dd` на 2 ГиБ падал с
`dd: IO error: Disk quota exceeded`. Файл создаётся в `/var/tmp` (корневой диск).

Проверка удаления объекта: код 204 не доказывает, что объект удалён (при сбое
`remove_object` клиент всё равно получает 204). Фактическое состояние проверяется
списком объектов в бакете. Место на томе MinIO освобождается с задержкой: объект
сначала уходит в `.minio.sys/tmp/.trash`.

### Presigned URL и хост (ловушка 1.1)

Подпись presigned URL считается в том числе по заголовку `Host`. Ссылка
создаётся локально, без обращения к MinIO: backend подписывает строку запроса
секретным ключом, а MinIO при скачивании строит такую же строку из того, что
увидел сам, и сравнивает.

Где ломалась подпись (опыт A): ссылка была подписана для `app.local`, но nginx
без `proxy_set_header Host` передал MinIO `Host: minio:9000`. Ответ:

    HTTP/1.1 403 Forbidden
    <Error><Code>SignatureDoesNotMatch</Code><Message>The request signature we
    calculated does not match the signature you provided. Check your key and
    signing method.</Message>...<Resource>/uploads/files/<id></Resource>...

В `Resource` путь пришёл без `/s3`, то есть `rewrite` сработал, расходился хост.

Решение:
1. Backend подписывает так, будто MinIO находится на `https://app.local`
   (второй клиент `minio` только для подписи, регион задан, в сеть он не ходит).
   Имя `minio:9000` в ссылку не попадает: оно существует только во внутренней
   сети Docker.
2. Префикс `/s3` дописывается после подписи.
3. nginx: `rewrite ^/s3/(.*)$ /$1 break;` отрезает префикс (при `proxy_pass` с
   переменной он сам URI не меняет) и `proxy_set_header Host $http_host;`
   передаёт Host таким, каким он пришёл.
4. Backend ходит в MinIO по `minio:9000` (внутренняя сеть), наружу открыт только
   путь `/s3/` и только для GET (`limit_except GET`).

Имя `minio` разрешается в момент запроса (`resolver` + переменная в `proxy_pass`),
поэтому остановленный MinIO не мешает `nginx -t` при деплое.

Проверено: ссылка скачивает файл (содержимое совпало с исходным); тот же URL с другим `Host`,
с изменённой подписью и методом PUT получает 403.

### Состояние MinIO при остановке и пересоздании контейнера

Данные лежат на `/srv/minio/data` (bind mount). Проверка: контейнер удалён
(`docker rm -f minio`), поднят заново (`docker compose up -d minio`),
SHA-256 скачанного объекта и список объектов в бакете совпали с состоянием до.

Поведение при недоступном MinIO:
- `GET /api/files/{id}/link` отвечает 200: ссылка подписывается локально и
  существование объекта или доступность MinIO не проверяет;
- скачивание по ссылке даёт 502 от nginx;
- загрузка до исправления отвечала 500 (traceback `Failed to resolve 'minio'`) и
  оставляла строку `pending`; теперь отвечает 503, строка получает статус `failed`;
- `nginx -t` и reload проходят: имя `minio` разрешается в момент запроса.


### MinIO: сохранность данных и поведение при остановке

Данные лежат на `/srv/minio/data` (bind mount). Проверка: контейнер удалён
(`docker rm -f minio`) и поднят заново (`docker compose up -d minio`);
SHA-256 скачанного объекта и список объектов в бакете совпали с состоянием до
удаления. Это доказывает сохранность данных при потере контейнера, но не при
потере самого тома: её проверит учение по восстановлению.

Поведение при недоступном MinIO (проверено и при `docker rm`, и при `docker stop`):
- `GET /api/files/{id}/link` отвечает 200: ссылка подписывается локально,
  доступность MinIO и существование объекта не проверяются;
- скачивание по ссылке даёт 502 от nginx (проверено при `docker rm`);
- загрузка раньше отвечала 500 и оставляла строку в статусе `pending`; теперь
  отвечает 503 `{"detail":"storage unavailable, try again later"}`, строка
  получает статус `failed`, в лог пишется `upload to storage failed: <ключ>`;
- причина в обоих случаях `NameResolutionError`: встроенный DNS Docker знает
  только имена запущенных контейнеров, поэтому остановленный MinIO выглядит как
  «имя не найдено», а не «соединение отклонено»;
- `nginx -t` и reload проходят: имя `minio` разрешается в момент запроса;
- `/health` остаётся 200;
- после `docker compose up -d minio` контейнер становится `healthy` примерно за 30 с.

Ограничение: если одновременно недоступен Postgres, `set_status('failed')` тоже
падает, и клиент получает 500 вместо 503.

## Согласованность Postgres и MinIO (этап 2)

Транзакции между Postgres и MinIO нет: любая операция, затрагивающая оба
хранилища, может оборваться посередине. Порядок выбран так, чтобы обрыв
оставлял безопасный мусор (объект, о котором никто не знает), а не опасный
(запись, которая ведёт в пустоту).

| Операция | Порядок |
|---|---|
| `POST /api/files` | 1. `INSERT` строки `pending` → 2. `PUT` объекта → 3. `UPDATE` статуса на `uploaded` |
| `DELETE /api/files/{id}` | 1. `DELETE` строки → 2. инвалидация кеша → 3. удаление объекта |

Три точки разрыва:

| Где оборвалось | Что остаётся | Что видит клиент | Кто находит |
|---|---|---|---|
| Загрузка: строка создана, `PUT` не прошёл (MinIO недоступен, падение backend) | строка `pending` или `failed`, объекта нет | `GET` показывает статус, `/link` отвечает 409 `file is not ready`, битой ссылки нет | сверка: `STALE_PENDING`; строки `failed` идут в `INFO` |
| Загрузка: `PUT` прошёл, `UPDATE uploaded` не выполнился | объект есть, строка `pending` | то же: 409, файл «ещё грузится» | сверка: `STUCK_PENDING`. Повтор с тем же `Idempotency-Key` через 10 минут забирает строку и перезаписывает объект под тем же ключом (по коду, отдельно не проверялось) |
| Удаление: строка удалена, объект остался | объект без строки, платим за хранение | 404, как и должно быть | сверка: `ORPHAN_OBJECT`; в логе backend `orphan object after row delete` |

Сценарий «объект загружен, записи нет» при загрузке невозможен из-за порядка
(строка создаётся первой). Он возникает при удалении и при ручной заливке в
bucket. Обратный порядок удаления (сначала объект, потом строка) при обрыве
оставил бы строку `uploaded` без объекта: `/link` выдал бы ссылку в пустоту,
а метаданные говорили бы, что файл существует. Это то самое состояние
`MISSING_OBJECT`, которое мы создали руками и которое нашла сверка. Лучше
потерянный объект: он стоит только места в хранилище, а клиент не получает
ошибку, о которой никто не знает.

### Сверка (reconciliation)

`backend/reconcile.py` сравнивает список объектов `files/` в bucket со строками
`files` и ищет четыре вида рассинхрона: `ORPHAN_OBJECT`, `MISSING_OBJECT`,
`STALE_PENDING`, `STUCK_PENDING`. Объекты и строки моложе
`RECONCILE_GRACE_MIN` (по умолчанию 10 минут) пропускаются: идущая в этот момент
загрузка выглядит как рассинхрон. Коды выхода: 0 рассинхронов нет, 10 найден
рассинхрон, 2 сверка не смогла отработать.

`scripts/reconcile.sh` запускает её внутри активного backend (там уже есть
`DATABASE_URL`, ключи S3 и сеть) и при коде 10 или любом другом ненулевом
отправляет сообщение в Telegram: сбой самой сверки тоже алертится,
«молчание» не означает «всё хорошо». Доставка проверена 2026-10-08: при
рукотворном рассинхроне отчёт пришёл в Telegram. Запуск: `systemd/reconcile.timer`
(`OnCalendar=*:0/30`, `Persistent=true`). Установка:

```bash
sudo install -m 755 scripts/reconcile.sh /usr/local/bin/reconcile.sh
sudo install -m 644 systemd/reconcile.service systemd/reconcile.timer /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now reconcile.timer
```

Доказательство (2026-10-08, `bash scripts/reconcile-proof.sh`, grace 0).
Рассинхрон создан мимо приложения: строка удалена SQL-ом, объект удалён и
залит через S3 API того же сервис-аккаунта (не через `mc`: алиасы `mc` живут на
tmpfs контейнера MinIO и пропадают при перезапуске).

| Что сделали руками | Что нашла сверка |
|---|---|
| удалили строку A в Postgres | `ORPHAN_OBJECT files/89b94b97-...` |
| залили объект `files/manual-orphan-test` | `ORPHAN_OBJECT files/manual-orphan-test` |
| удалили объект B в MinIO | `MISSING_OBJECT id=59684eed-...` |

Итог: `RESULT orphan_objects=2 missing_objects=1 stale_pending=0 stuck_pending=0`,
код 10. После уборки: все нули, код 0.

### Идемпотентность

Операция идемпотентна, если её повтор даёт то же состояние, что и одно
выполнение. Загрузка по сети без этого свойства опасна: клиент не знает, дошёл
ли запрос, повторяет его и получает два файла.

Ключ идемпотентности клиент задаёт заголовком `Idempotency-Key` (до 128
символов, `[A-Za-z0-9._:-]`), он хранится в колонке `files.idempotency_key` с
частичным `UNIQUE`-индексом (миграция `005_idempotency.sql`). Повтор с тем же
ключом возвращает 200, `"duplicate": true` и прежний `id`. Проверено:
первый запрос 201, второй 200 с тем же `id`, в списке одна строка.

Почему ключ задаёт клиент, а не хеш содержимого: хеш известен только после
чтения всего файла, а два разных пользователя могут загрузить одинаковые байты,
и это две разные операции. Ключ описывает намерение «эта загрузка», а не
содержимое. Загрузка без заголовка не идемпотентна (каждый запрос даёт новую
строку). Повтор, пока первая загрузка ещё идёт (`pending` младше 10 минут),
получает 409 (по коду, отдельно не проверялось).

## Redis как кеш (этап 3)

`GET /api/files/{id}`: ключ `file:<id>` в Redis, при промахе одна загрузка из
Postgres и запись в кеш. Кеш не источник правды: любой ключ можно потерять, и
система просто сходит в Postgres. Если Redis перезапустится и потеряет всё,
это волна промахов и временный рост нагрузки на БД, но не потеря данных.

- **TTL с разбросом.** 60 секунд плюс случайные 0–30%. Тысяча ключей с одним
  TTL, записанных одновременно, истекают в одну секунду и дают
  одновременный поход в БД: будущий инцидент. Разброс размазывает истечения.
- **Инвалидация.** Ключ удаляется при загрузке, повторной загрузке, смене статуса
  и удалении. Проверено `scripts/cache-proof.sh` (результат в CHAOS.md и ниже).
- **Падение Redis не роняет API.** Таймаут сокета 0.3 с; после ошибки Redis
  обходится на 5 секунд (выключатель), чтобы не платить таймаут на каждом
  запросе. В логе `redis unavailable (...)`, метрика `cache_errors_total`.
  Проверено:

| Состояние Redis | Результат запроса |
|---|---|
| `docker stop redis` (имя пропадает из DNS Docker) | 200 за 0.054 с, `/health` 200, `/health/deps` показывает `redis: degraded` |
| `docker pause redis` (сокет молчит) | первый запрос 200 за 0.354 с (сработал таймаут), следующие 200 за ~0.01 с (выключатель) |

- **Cache stampede.** 200 одновременных запросов за ключом, которого нет в
  кеше (`backend/stampede_test.py`; загрузка из БД замедлена до 200 мс файлом-флагом,
  чтобы промахи были одновременными):

| Режим | Ушло в Postgres | Ошибок кеша |
|---|---|---|
| без single-flight | 40 | 0 |
| с single-flight (блокировка на ключ) | 1 | 0 |

«40» вместо 200: синхронные ручки выполняются в пуле из 40 потоков (значение по
умолчанию), остальные запросы ждут очереди и попадают уже в заполненный кеш.

### Health: liveness и readiness

- `/live`: процесс жив и отвечает. Зависимостей нет. Если не отвечает, процесс
  надо перезапускать.
- `/health` (readiness): можно ли слать трафик. Зависит только от Postgres
  (503, если недоступен). Redis и MinIO сюда не входят: без них сервис
  деградирует, но работает.
- `/health/deps`: информационная проверка Postgres, Redis, MinIO, никогда не 5xx.

Деплой не переключает nginx, пока `/health` нового контейнера не ответил за 10
попыток: так и произошло 2026-10-08, когда в образ не попали новые модули
(контейнер не запустился, `deploy.sh` удалил его, старый цвет продолжил
обслуживать трафик). Поведение при недоступном Postgres (503) проверяется в
CHAOS.md, эксперимент 3.

### Перезапуск Postgres и мёртвые соединения пула

Найдено 2026-10-09. В 06:12:25 UTC на VM-2 стартовал `apt-daily-upgrade`
(unattended-upgrades), в 06:12:33 `postgresql@18-main` был перезапущен (в
`unattended-upgrades-dpkg.log`: `Restarting services... systemctl restart
postgresql@18-main.service`, то есть `needrestart`). По порядку строк рестарт идёт
сразу после обновления `libxml2-16`; прямой отметки, какой пакет его вызвал,
нет. Postgres был остановлен и снова готов в пределах 0.15 с (`database system
is shut down` в 06:12:33.717, `ready to accept connections` в 06:12:33.870).
Такие рестарты повторятся при каждом обновлении библиотек.

Postgres вернулся сразу, а `/health` оставался красным: пять 503 подряд с
06:12:35 по 06:14:06, везде `SSL connection has been closed unexpectedly`,
ровно по числу соединений пула backend (5). Worker (пул из 2 соединений) дважды
получил сбой sweeper (06:12:37 и 06:13:38). Раньше этот раздел говорил, что 503
бывает только при падении Postgres, а `/health` был красным около 90 с при
рабочей базе.

Механизм: `ThreadedConnectionPool._getconn` берёт `self._pool.pop()`, то есть
последнее возвращённое соединение (исходники psycopg2 в контейнере). Пул не знает,
что сервер оборвал сессии, и узнаёт это, только когда запрос воспользуется
соединением. Каждое из пяти соединений стоило одного упавшего запроса, а `putconn`
закрывает соединение со статусом `TRANSACTION_STATUS_UNKNOWN`, поэтому после
пяти ошибок пул вылечивался сам. Время выздоровления определяла не скорость
рестарта (3 с), а частота запросов: при пробе раз в 30 с вышло около 90 с.

Воспроизведено: `systemctl restart postgresql@18-main` на VM-2, цикл
`curl /health` раз в секунду 130 секунд (`evidence/pg-restart-before.txt`,
`evidence/pg-restart-after.txt`).

| | До | После |
|---|---|---|
| ответы `/health` | 125 × 200, 5 × 503 | 130 × 200 |
| ошибок `postgres check failed` в логе backend | 5 | 0 |
| сбоев sweeper у worker | 2 (09:20:49, 09:21:50) | 0 |
| `db_pool_stale_total` | счётчика не было | 5 |
| статус Docker healthcheck | `healthy` во всех строках | `healthy` во всех строках |

«До»: рестарт Postgres в 09:20:29–09:20:31 UTC, пул пересоздан командой
`docker restart backend-green worker` (7 соединений `appuser` в `pg_stat_activity`).
«После»: рестарт в 09:32:03–09:32:06 UTC, пул свежий после `./deploy.sh`. Первый
прогон «до» (09:08) дал одну ошибку: перед пересозданием в `pg_stat_activity`
было 2 соединения `appuser` вместо 7, после инцидента 06:12 пул ужался. В
таблице второй прогон, на полном пуле.

Исправление: `backend/db.py`, функция `_checkout`. При выдаче из пула
соединение проверяется запросом `SELECT 1` (в `autocommit`, без `BEGIN` и
лишнего круга на `ROLLBACK`). Мёртвое закрывается (`putconn(close=True)`,
счётчик `db_pool_stale_total`), берётся следующее, до `maxconn + 1` попыток:
если мертвы все, откроется новое. Проверка выключается файлом-флагом
`NO_PREPING` (как `NO_POOL`) для замеров. Повторять сам запрос после ошибки не
стали: для неидемпотентных запросов (`INSERT` загрузки) это небезопасно, а
проверка до запроса повторять не требует.

Что не проверено и не покрыто:

- Реальное окно недоступности Postgres занимает 0.15 с, при пробе раз в секунду
  в него никто не попал. Поведение при долгой остановке: `CHAOS.md`, эксперимент 3.
- Тихий обрыв сети (пакеты пропадают без RST): `SELECT 1` будет ждать. Значения
  `connect_timeout` и TCP keepalive в `DATABASE_URL` не проверялись.
- Запрос, который шёл в момент остановки Postgres, по-прежнему получит ошибку.
- В инциденте 06:12 пробы Docker вернули 503 четыре раза подряд при `Retries: 3`,
  но смена статуса на `unhealthy` не проверена: `docker events` за то время
  ничего не вернул.

## Redis как очередь (этап 4)

После загрузки файл получает статус `uploaded`, backend кладёт задачу в очередь,
`worker` считает SHA-256, размер и тип файла и пишет результат в Postgres
(статус `done`).

### 4.1 Наивная версия: список и BRPOP

Продюсер делает `LPUSH`, воркер забирает задачу `BRPOP` и обрабатывает.
Подтверждения нет. Опыт: `bash scripts/stage4-proof.sh naive` (воркер в режиме
`WORKER_MODE=naive`, обработка одной задачи 30 с), 2026-10-08:

| Шаг | Что наблюдал |
|---|---|
| 3 файла загружены, `LPUSH` | в списке 3 задачи |
| через 8 с | `LLEN=2`, у первого файла статус `processing` |
| `docker kill worker-naive` посреди обработки | `LLEN=2`: первой задачи нет ни в списке, ни у кого |
| новый воркер, 10 с | файлы 2 и 3 `done`, файл 1 так и остался `processing` |

Почему так вышло: `BRPOP` удаляет элемент из списка в момент выдачи. С этой
секунды единственный носитель задачи — память процесса воркера. Процесс убит,
задача исчезла, а в Postgres осталась строка в статусе `processing`, и ничто в
системе этого не исправит. Это at-most-once: задача выполнится не более одного
раза, возможно, ни разу.

### 4.2 Правильная версия: Redis Streams с consumer group

| Механизм | Как сделано |
|---|---|
| Постановка | `XADD queue:files` после статуса `uploaded`. Если Redis недоступен, загрузка всё равно успешна, файл остаётся `uploaded` |
| Выдача | `XREADGROUP`, группа `workers` |
| Подтверждение | `XACK` и `XDEL` только после записи результата в Postgres |
| Возврат зависших | каждые 5 с `XPENDING` с простоем больше `MIN_IDLE_S` (60 с по умолчанию, в опыте 15 с), затем `XCLAIM` и повторная обработка |
| Лимит повторов | `MAX_DELIVERIES=3`: после трёх доставок задача уходит в `queue:files:dead`, файл получает статус `failed`, в логе `DEAD LETTER` |
| Сторож | раз в минуту файлы `uploaded` дольше 2 минут или `processing` дольше 10 минут ставятся в очередь заново |

Обработчик идемпотентен: файл в статусе `done` пропускается, а результат
пишется только из `uploaded` или `processing` (`UPDATE ... WHERE status IN
(...)`). Повторная доставка той же задачи даёт тот же хеш и ничего не портит.

Сторож закрывает потерю задачи в самом Redis (AOF с `everysec` может потерять
последнюю секунду записей) и сбой `XADD` при загрузке. Сработал на практике: при
старте worker он поставил в очередь файл, который висел в `uploaded`, пока воркера
не было (`sweeper re-enqueued id=d5255f94-...`).

Доказательство, `bash scripts/stage4-proof.sh streams`: 10 файлов, обработка 3 с
на файл, `docker kill worker` через 8 с. На момент kill 2 файла `done`, 1
`processing`, 7 `uploaded`. После `docker start worker` все 10 стали `done` за
25 с. Для каждого файла `processed ok` встретился в логе ровно один раз, SHA-256
совпал с `sha256sum` исходного файла, зависшая задача вернулась один раз
(`reclaimed stuck task`).

Мёртвая очередь, `bash scripts/stage4-proof.sh dlq`: объект удалён до обработки,
воркер получает `NoSuchKey`. Три доставки по 15 с простоя, на 45-й секунде
`dead=1`, в `queue:files:dead` лежат `file_id`, `orig_id`, `reason=delivered 3
times without ack`, файл в статусе `failed`.

Что видно по очереди (`bash scripts/queue-stats.sh`):

```
queue: waiting=0 in_flight=1 oldest_age_s=31.4 dead=0 naive_list=0
```

`oldest_age_s` — возраст самой старой невыполненной задачи (включая выданные
без подтверждения). Он важнее длины: очередь из одной задачи, которая стоит
час, хуже очереди из ста, которые разбираются.

Ограничение: `MIN_IDLE_S` должен быть больше самой долгой обработки. Иначе
живой, но медленный воркер получит дубль своей задачи. Данные от этого не
портятся (обработчик идемпотентен), но работа выполняется дважды.

### Вопросы этапа

**At-least-once и почему at-most-once здесь неприемлемо.** At-least-once: задача
будет выполнена минимум один раз, при сбоях возможны повторы. At-most-once: не
более одного раза, при сбое задача пропадает (опыт 4.1). Для обработки файла
потеря хуже повтора: файл навсегда остаётся «в обработке», и никто об этом не
знает, а повторное вычисление хеша ничего не стоит.

**Почему «ровно один раз» на практике означает «хотя бы один раз +
идемпотентность».** Воркер может умереть после записи результата, но до
подтверждения. Брокер не может отличить это от смерти до записи, поэтому задача
выдаётся повторно. Исключить повтор нельзя, можно сделать его безвредным: тогда
эффект получается «как будто ровно один раз».

## Пулы соединений и замеры (этап 5)

Соединение с Postgres не открывается на каждый запрос: `backend/db.py` держит
`ThreadedConnectionPool` на 5 соединений (`DB_POOL_MAX`) и ждёт свободное до 2 с
(`DB_POOL_TIMEOUT`). При исчерпании клиент получает 503 с `Retry-After: 1`, а не
зависание и не 500. Запрос не может держать соединение вечно:
`statement_timeout` 8 с (`DB_STATEMENT_TIMEOUT_MS`), по истечении 503. К Redis
соединения тоже из пула (`redis.ConnectionPool`, 64 соединения, таймаут сокета
0.3 с у кеша). `DB_POOL_MIN` по умолчанию равен `DB_POOL_MAX`: у
`ThreadedConnectionPool` соединения сверх `minconn` закрываются при возврате,
и при `min=1` пул под нагрузкой превращался бы в «соединение на запрос».
Эндпоинт `/items` раньше открывал соединение на каждый запрос, теперь работает
через пул (исправлено 2026-10-08). Каждое соединение проверяется при выдаче из
пула запросом `SELECT 1` (с 2026-10-09): причина и цифры в разделе «Перезапуск
Postgres и мёртвые соединения пула», цена проверки ниже.

Замеры: `bash scripts/bench.sh`, ручка `GET /api/files/{id}`, `wrk -t2 -c50`.
Режимы переключаются файлами-флагами в томе backend (`NO_POOL`: соединение на
запрос, `NO_CACHE`: кеш обойдён), без перезапуска. wrk, nginx, backend, Redis
и MinIO работают на одной VM-1, Postgres на VM-2. Абсолютные числа из-за этого
занижены, показательно соотношение между строками.

| Режим | RPS | p50, мс | p95, мс | p99, мс | Прогонов |
|---|---|---|---|---|---|
| без пула / без кеша | 300 | 159.2 | 230.9 | 266.1 | 1 по 20 с |
| без пула / с кешем | 1687 | 28.6 | 40.7 | 48.9 | медиана 3 по 15 с |
| с пулом / без кеша | 916 | 52.4 | 74.8 | 105.0 | 1 по 20 с |
| с пулом / с кешем | 1649 | 29.1 | 42.1 | 51.2 | медиана 3 по 15 с |

Что видно: пул поднимает RPS с 300 до 916, а p50 снижает со 159 до 52 мс.

### Арифметика пула

Замерено на VM-2: `max_connections` = 100, `superuser_reserved_connections` = 3.

| Статья | Соединений |
|---|---|
| доступно обычным ролям (100 − 3) | 97 |
| штатно: 1 backend × 5 + worker × 2 | 7 (в `pg_stat_activity` `appuser`: 7) |
| деплой blue/green: 2 backend × 5 + worker × 2 | 12 |
| запас: сверка, миграции, ручной `psql` | 10 |
| итого в пике деплоя | 22 из 97 |

Для k копий backend с одновременным деплоем: 2·k·5 + 2 + 10 ≤ 97, то есть k ≤ 8.
Бэкап Postgres подключается ролью `postgres` и может занять зарезервированные
слоты.

### Опыт: что происходит при исчерпании лимита соединений

Глобальный `max_connections` без перезапуска всей базы не снизить, поэтому
опыт сделан на лимите роли: `ALTER ROLE appuser CONNECTION LIMIT 8` (штатно роль
держит 7 соединений). Лимит поставлен на VM-2 в 12:39:34 UTC, возврат на `-1`
выполнен вручную в 12:42 (таймер systemd на автовозврат был поставлен, но
сработать не успел, поэтому автовозврат не проверен). 2026-10-08, VM-1:
`./deploy.sh` с лимитом 8.

| Что | Результат |
|---|---|
| деплой | `rc=1` за 65 с (12:39:52–12:40:57 UTC), 10 попыток health-check, затем откат |
| новый контейнер | не стартовал: в логе Postgres `FATAL:  too many connections for role "appuser"` (12:40:14, 12:40:28, 12:40:55) |
| старый цвет | не тронут, `healthy`, `/health` отвечает 200 |
| worker | не пересоздавался, деплой остановился до его обновления |

Вывод: новому контейнеру при деплое нужны ещё 5 соединений. При штатных лимитах
(22 из 97 в пике, см. арифметику выше) это не проблема, но лимит ниже пика
деплоя превращает деплой в отказ с откатом, а не в падение сервиса. Глобальный
`max_connections` даёт другое сообщение (`sorry, too many clients already`), но
это из документации, на нашей базе не проверялось.

### Почему пул на 200 соединений — не «быстрее»

Каждое соединение с Postgres — отдельный процесс с собственной памятью. Пул на
200 не укладывается в `max_connections` = 100 и не стартует. Если лимит поднять,
скорость всё равно не вырастет: параллельно база выполняет столько запросов,
сколько у неё ядер, остальные конкурируют за процессор и блокировки. Очередь
перемещается из дешёвого ожидания в приложении (пул отвечает 503 через 2 с) в
дорогое ожидание внутри базы, где все 200 соединений тормозят друг друга. Размер
пула умножается на число инстансов и перекрывается при деплое, поэтому один
сервис с большим пулом занимает слоты, нужные остальным (worker, сверка, бэкап),
и перегрузка одного сервиса становится отказом всей базы.

## Порты и доступность

Проверено 2026-10-07 (SSH, 9090 и кластер повторно после перезагрузки VM-1 2026-10-08): `docker ps`, `ss -tuln`, `iptables -S DOCKER-USER`,
`ufw status` на VM-1 и запросами с Mac (хост UTM, подсеть 192.168.64.0/24).

| Порт | Что | Где | Кто может подключиться | Как проверено |
|---|---|---|---|---|
| 443 | nginx, TLS: `/api/*` и `/s3/*` (только GET) | VM-1, публикует Docker | любой клиент, достигающий VM-1 | `docker ps`, ответы nginx |
| 80 | nginx, редирект на 443 | VM-1 | любой клиент | `docker ps`, `ufw status` |
| 8000 | backend (blue или green) | app-net | только контейнеры app-net | `docker ps`: не опубликован |
| 9000 | MinIO S3 API | app-net | только app-net; снаружи только presigned GET через `/s3/` | `docker ps`; PUT по ссылке снаружи даёт 403 от nginx |
| 6379 | Redis | app-net | только app-net, нужен пароль | `redis-cli ping` без пароля: `NOAUTH` |
| 9090 | Prometheus | VM-1, публикует Docker | только VM-2 (192.168.64.5) | правило в `DOCKER-USER`; после ребута VM-1 правило на месте, с Mac таймаут по IPv4 и IPv6 (2026-10-08) |
| 8080, 9100 | cAdvisor, node-exporter | monitoring-net | только Prometheus внутри сети, наружу не опубликованы | с Mac таймаут (до правки отвечали 200) |
| 5432 | PostgreSQL 18 | VM-2 | только VM-1 | `db` = 192.168.64.5; с Mac таймаут |
| 22 | sshd | VM-1 | только подсеть 192.168.64.0/24 (UFW) | `ufw status`; вход с Mac проходит (2026-10-08) |
| 3000 | Grafana | VM-2 | только оператор | по README задания 3, сегодня не перепроверялось |

Docker публикует порты через `DNAT`, и такие пакеты идут через `FORWARD`,
минуя `INPUT`, где работает UFW. Для опубликованных портов (443, 80, 9090)
UFW не действует, единственный фильтр это цепочка `DOCKER-USER`. Неопубликованный
порт защищён UFW как обычный порт хоста: политика deny даёт таймаут.

Найденное при проверке: cAdvisor и node-exporter были опубликованы на 0.0.0.0
без фильтра (с Mac отвечали 200), публикация убрана, Prometheus ходит к ним
по именам внутри monitoring-net. На VM-1 работал забытый Postgres из
задания 2 (кластер 18/main, только таблица `items`), он остановлен и отключён (`start.conf` = `disabled`:
при `auto` кластер оказался online, хотя был остановлен), правило UFW для 5432 удалено:
backend использует Postgres на VM-2.
